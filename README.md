# Codryx Store Bot

النظام الداخلي لإدارة منتجات Codryx.

## التثبيت

```bash
npm install
cp .env.example .env
# عدّل .env بالقيم الصحيحة (لا تنسَ CLIENT_ID والرتب)
```

## ⚠️ خطوة مهمة: تفعيل Server Members Intent

من [Discord Developer Portal](https://discord.com/developers/applications) → Bot →
فعّل **Server Members Intent** تحت Privileged Gateway Intents.

## ⚠️ خطوة مهمة: تسجيل Slash Commands

```bash
node deploy-commands.js
```

ثم شغّل البوت:

```bash
node bot.js
```

## رتب متعددة

تقدر تضيف أكثر من رتبة لكل صلاحية، مفصولة بفاصلة بدون مسافات:

```
OWNER_ROLE_IDS=111111111111111111,222222222222222222
SUPPORT_ROLE_IDS=333333333333333333,444444444444444444
DEV_ROLE_IDS=555555555555555555
CLOSE_ROLE_IDS=111111111111111111,666666666666666666
```

- **OWNER_ROLE_IDS** — صلاحيات كاملة (تشمل كل الأوامر تلقائيًا، وتعتبر دائمًا "Closer")
- **SUPPORT_ROLE_IDS** — يستلم تذاكر الدعم الفني / الاستفسار / البلاغ، ويقدر يستلم أي تذكرة
- **DEV_ROLE_IDS** — يستلم تذاكر شراء المنتجات / التطوير الخاص، ويرى أوامر `/orders` و `/order`
- **CLOSE_ROLE_IDS** — الرتب الوحيدة المسموح لها بحذف التذاكر فعليًا بعد طلب الإغلاق (مستقلة تمامًا عن باقي الرتب، إلا أن Owner يملكها دائمًا)
- **DASHBOARD_ROLE_IDS** — الرتب المخوّلة باستخدام `/products` وكل أزرار إدارة المنتجات وطرق الدفع وتاريخ العملاء (Founder/CEO/Developer مثلًا)

## إعداد تذكير التذاكر غير المستلمة

أضف في `.env` اختياريًا:

```env
UNCLAIMED_TICKET_REMINDER_MINUTES=10
```

القيمة الافتراضية 10 دقائق. إذا بقيت التذكرة بدون استلام، يُرسل البوت تذكيرًا للفريق المخصص مرة واحدة، ويستعيد المؤقت بعد إعادة تشغيل البوت.

## آلية التذاكر

1. العميل يفتح القناة التي فيها البانل (`/panel`)
2. يختار نوع طلبه **مباشرة من القائمة في البانل** (لا حاجة لفتح تذكرة أولًا)
3. يُفتح له تذكرة بالنوع المختار تلقائيًا
4. **لا يمكنه فتح تذكرة أخرى من نفس النوع** وهو لا يزال لديه واحدة مفتوحة — لكن يمكنه فتح أنواع أخرى بالتوازي
5. حسب النوع:
   - **شراء منتج** → يختار منتج وخطة → يُنشأ أوردر ويُمنشن **فريق التطوير**
   - **دعم فني / استفسار / بلاغ** → يُمنشن **فريق الدعم**
   - **تطوير خاص** → يُمنشن **فريق التطوير**

لا يوجد "تجهيز بالنفس" — الفريق هو من يتولى كل الإعداد دائمًا بعد التواصل مع العميل.

## استلام التذاكر وإغلاقها

كل تذكرة (شراء أو دعم أو غيره) تحتوي على زرين تظهر فيها جميعًا بنفس الطريقة:

- **🙋 استلام التذكرة** — مخصص حسب نوع التذكرة:
  - **شراء منتج / تطوير خاص** → فقط فريق التطوير (`DEV_ROLE_IDS`) أو المالك يقدروا يستلموا
  - **دعم فني / استفسار / بلاغ** → فقط فريق الدعم (`SUPPORT_ROLE_IDS`) أو المالك يقدروا يستلموا
  - بعد الاستلام يُسجَّل اسم المستلم ويختفي الزر تلقائيًا
- **🔒 طلب إغلاق** — يظهر لأي شخص يرى التذكرة (بما فيهم العميل نفسه). الضغط عليه لا يحذف التذكرة فورًا:
  - لو الضاغط يملك رتبة من `CLOSE_ROLE_IDS` → يظهر له زر تأكيد الحذف مباشرة
  - لو لا يملكها → تُمنشن رتب `CLOSE_ROLE_IDS` لمراجعة الطلب والتأكيد

هذا يفصل بين "من يقدر يرى التذكرة ويطلب إغلاقها" (الجميع) و"من يقدر يحذفها فعليًا" (رتب محددة فقط في `CLOSE_ROLE_IDS`).

## نظام حالات الأوردر والدفع

كل أوردر شراء يمر بمراحل واضحة، وكل تغيير حالة عادي يُحدث 3 أشياء تلقائيًا:
1. رسالة في تذكرة العميل
2. رسالة خاصة (DM) للعميل
3. تحديث الإيمبيد في روم لوج الأوردرات (في مكانه، بدون رسالة جديدة)

### الحالات المتاحة (بالترتيب)

| الحالة | الوصف |
|--------|-------|
| 🟡 `pending_review` | بانتظار المراجعة (تلقائية عند إنشاء الأوردر) |
| 🔵 `in_progress` | جاري التجهيز |
| 🟣 `testing` | مرحلة الاختبار من قبل العميل |
| ✅ `testing_done` | تم الانتهاء من الاختبار |
| 💰 `awaiting_payment` | بانتظار الدفع (تفتح Modal تحديد السعر تلقائيًا) |
| 🟠 `payment_pending` | جاري الدفع (بعد اختيار العميل طريقة الدفع) |
| 💳 `paid` | تم الدفع (بعد تأكيد المسؤول عن المالية) |
| 📦 `delivered` | تم التسليم |
| 🔴 `cancelled` | ملغي |

لتغيير أي حالة عادية: اذهب إلى روم لوج الأوردرات، تحت كل أوردر توجد قائمة اختيار. هذا الإجراء مخصص لفريق التطوير (`DEV_ROLE_IDS`) أو المالك.

### دورة الدفع الكاملة (خطوة بخطوة)

**1. تحديد السعر** — من قائمة الحالة في روم اللوج، اختر **"بانتظار الدفع"**. هذا يفتح نافذة (Modal) فورًا لإدخال:
- السعر الأصلي (مطلوب)
- قيمة الخصم (اختياري)
- سبب الخصم (اختياري)

بعد التأكيد: يُحفظ السعر، تتحول الحالة لـ `awaiting_payment`، ويُرسل للعميل (DM + رسالة تذكرة) + **رسالة بأزرار اختيار طريقة الدفع داخل تذكرته** (محفظة / إنستا باي / بايننس).

**2. العميل يختار طريقة الدفع** — بالضغط على أحد الأزرار في تذكرته:
- تُحفظ الطريقة المختارة
- تتحول الحالة لـ `payment_pending`
- تُرسل رسالة "سيتواصل معك المسؤول عن المالية" + **منشن فريق المالية** (`FINANCE_ROLE_IDS`) في تذكرة العميل

**3. تأكيد استلام الدفع** — في روم اللوج، يظهر زر **"✅ تم الدفع"** تحت الأوردر (فقط أثناء حالة `payment_pending`). هذا الزر مخصص لـ `FINANCE_ROLE_IDS` فقط:
- تتحول الحالة لـ `paid`
- يُرسل DM + رسالة تذكرة بتفاصيل الدفع والخصم
- **تُرسل دعوة تقييم (Feedback) للعميل في تذكرته مباشرة** (انظر قسم نظام التقييم أدناه)
- **يتحدث روم العملاء تلقائيًا** بالإحصائيات الجديدة

السعر النهائي = السعر الأصلي − الخصم. كل التفاصيل محفوظة بشكل دائم في بيانات الأوردر.

### تعديل رسائل الحالات

كل رسالة (تذكرة + DM) لكل حالة معرّفة في ملف واحد: `core/orderStatus.js`. لتعديل نص أي رسالة، عدّل دالة `customerDM` أو `ticketMessage` للحالة المطلوبة — لا حاجة للبحث في أي مكان آخر.

## طرق الدفع (قابلة للتخصيص بالكامل)

كل طرق الدفع معرّفة في ملف واحد: `config/paymentMethods.js`. الأزرار والرسائل في كل التذاكر تُبنى تلقائيًا من هذا الملف — لا حاجة لتعديل أي كود آخر.

### إضافة طريقة دفع جديدة

افتح `config/paymentMethods.js` وأضف عنصرًا جديدًا داخل `PAYMENT_METHODS`:

```js
{
  id: 'vodafone_cash',           // معرّف فريد بدون مسافات (يُستخدم داخليًا)
  active: true,                  // false لتعطيلها مؤقتًا بدون حذفها
  label: 'فودافون كاش',          // الاسم الظاهر على الزر
  emoji: '🔴',                   // الإيموجي الظاهر على الزر
  instructions: 'يمكنك التحويل على رقم: **01000000000**', // يظهر للعميل بعد اختيار هذه الطريقة
},
```

بعد الحفظ، أعد تشغيل البوت (أو `/reload` إن كان مفعّلاً لإعادة تحميل الإعدادات) — الزر الجديد سيظهر تلقائيًا لكل عميل يصل لمرحلة اختيار طريقة الدفع، بدون أي تعديل في أي ملف آخر.

### حذف أو تعطيل طريقة

غيّر `active` إلى `false`، أو احذف العنصر بالكامل من القائمة.

## سجلات التذاكر (Transcripts)

عند إغلاق أي تذكرة (من أي نوع: شراء، دعم، استفسار، تطوير خاص، بلاغ)، يقوم البوت تلقائيًا بـ:

1. جمع كل الرسائل في التذكرة (نصوص، إيمبيدات، مرفقات، أزرار/قوائم) بالترتيب الزمني
2. بناء ملف HTML واحد منسّق بشكل شبيه بواجهة Discord، يحتوي على:
   - نوع التذكرة، صاحبها، تاريخ الفتح والإغلاق، ومن أغلقها
   - كل رسالة بصورة الكاتب واسمه ووقتها ومحتواها كاملًا
3. رفع الملف لقناة `TRANSCRIPT_LOG_CHANNEL_ID` **قبل** حذف القناة فعليًا

هذا يحدث تلقائيًا عند كل إغلاق تذكرة — لا حاجة لأي إجراء إضافي. لو لم تحدد `TRANSCRIPT_LOG_CHANNEL_ID`، يتم تجاهل هذه الخطوة تمامًا بدون أي تأثير على باقي عملية الإغلاق.

### تخصيص شكل السجل

التنسيق الكامل (الألوان، الخطوط، شكل الإيمبيدات) موجود في دالة `buildTranscript` داخل `handlers/transcriptHandler.js` ضمن متغير `<style>` — يمكنك تعديله مباشرة لتغيير المظهر.

## نظام تقييم العملاء (Feedback)

بعد تأكيد المسؤول المالي استلام الدفع (`paid`)، تُرسل تلقائيًا في تذكرة العميل رسالة دعوة للتقييم مع 5 أزرار (⭐ إلى ⭐⭐⭐⭐⭐).

### الفلو

1. العميل يضغط على عدد النجوم الذي يعكس تجربته
2. تظهر نافذة (Modal) لكتابة ملاحظة أو سبب التقييم (اختياري تمامًا — يمكن تركه فاضيًا)
3. بعد الإرسال: يُحفظ التقييم بشكل دائم، تُرسل رسالة شكر للعميل في تذكرته، ويُرسل التقييم الكامل (مع اسم العميل، المنتج، عدد النجوم، والملاحظة) إلى `FEEDBACK_CHANNEL_ID`

لا يمكن للعميل تقييم الطلب نفسه أكثر من مرة واحدة.

### تعديل نص الدعوة

نص دعوة التقييم (نفس النص المرسل في الطلب الأصلي) موجود في دالة `feedbackInvitation()` داخل `core/embeds.js` — عدّله مباشرة لتغيير الصياغة.

## روم العملاء

لو حددت `CUSTOMERS_CHANNEL_ID` في `.env`، يُنشئ البوت رسالة واحدة دائمة في هذه القناة تعرض كل العميل اللي أتموا الشراء، مرتبين حسب الأكثر صرفًا، مع عدد طلباتهم وإجمالي ما دفعوه. هذه الرسالة تتحدث في مكانها تلقائيًا بعد كل عملية دفع مؤكدة — لا تتكرر رسائل جديدة.

لو سيبت `CUSTOMERS_CHANNEL_ID` فاضية، هذه الميزة تُعطَّل تلقائيًا بدون أي تأثير على باقي النظام.

## لوحة إدارة المنتجات (Product Dashboard)

استخدم `/products` لإنشاء لوحة إدارة ثابتة داخل أي قناة. هذا الأمر **لا يُنشئ أكثر من لوحة واحدة في السيرفر** — لو نُفّذ مرة أخرى:
- لو اللوحة موجودة وسليمة → يُحدّثها في مكانها فقط (نفس الرسالة)
- لو محذوفة أو القناة محذوفة → يُنشئ لوحة جديدة وينسى القديمة تلقائيًا

كل تعديل (إضافة منتج، تغيير سعر، تغيير حالة...) **يحدّث اللوحة الرئيسية تلقائيًا في مكانها بدون أي restart**.

### الصلاحية

`/products` مخفي تلقائيًا عن الأعضاء العاديين (يتطلب صلاحية "Manage Server" من ديسكورد نفسه لرؤيته في القائمة)، وبالإضافة لذلك يتحقق الكود من رتب `DASHBOARD_ROLE_IDS` في `.env` كطبقة أمان إضافية. لو لم تحدد هذه الرتب، يقتصر الوصول على المالك (`OWNER_ROLE_IDS`) فقط.

### اللوحة الرئيسية

تعرض: عدد المنتجات الكلي، المتاحة، تحت الصيانة، المخفية، إجمالي الطلبات، إجمالي المبيعات. وتحتها 5 أزرار:

- **➕ إضافة منتج** — يبدأ Wizard من 3 نوافذ متتالية (الاسم/الوصف/الفئة/الإصدار، ثم اللون/الصور/المميزات، ثم الباقة الأولى) وينشئ ملف `product.json` تلقائيًا
- **✏️ تعديل منتج** — قائمة اختيار تعرض كل المنتجات، وبعد الاختيار تظهر لوحة المنتج الكاملة
- **👁️ عرض المنتجات** — قائمة سريعة بكل المنتجات وحالاتها
- **📊 الإحصائيات** — عدد المنتجات، الطلبات، أكثر/أقل منتج مبيعًا، إجمالي المبيعات
- **⚙️ الإعدادات** — عرض الرتب المخوّلة الحالية

### لوحة منتج واحد

بعد اختيار منتج، تظهر لوحته الكاملة (الاسم، الوصف، الفئة، الإصدار، السعر، الصورة، الحالة، آخر تحديث، عدد طلباته) مع أزرار التحكم:

| الزر | الوظيفة |
|------|---------|
| 🟢 تفعيل / 🟡 صيانة | تبديل `availability` — يتحكم في إمكانية الشراء |
| 👁️ إظهار / 🔴 إخفاء | تبديل `visibility` — يتحكم في ظهور المنتج بالمتجر |
| 🏷️ Badge | فتح قائمة لاختيار شارة (NEW/POPULAR/FEATURED/PREMIUM/UPDATED) أو إزالتها |
| ✏️ الاسم / 📝 الوصف / 💰 السعر / 🎨 اللون | كل واحد يفتح نافذة (Modal) للتعديل المباشر |
| 🖼️ الصور | نافذة لإدخال روابط Thumbnail و Banner |
| ⭐ المميزات | نافذة واحدة تكتب فيها كل ميزة في سطر مستقل |
| 📦 الباقات | قائمة لاختيار باقة موجودة للتعديل أو إضافة باقة جديدة (اسم، سعر، عملة، مميزات) |
| 🔄 الإصدار | نافذة لتحديث رقم الإصدار |
| ⬆️⬇️ الترتيب | نقل المنتج لأعلى/أسفل في قائمة المتجر |
| 🔄 تحديث الرسالة | إعادة رسم لوحة المنتج يدويًا (نادرًا ما يُحتاج إليه، التحديث تلقائي) |

### Visibility و Availability (مفهومان منفصلان)

- **Visibility** (`visible` / `hidden`): يتحكم هل المنتج يظهر في قائمة المتجر للعميل أصلًا أم لا
- **Availability** (`active` / `maintenance`): يتحكم هل يمكن شراء المنتج. منتج `maintenance` **يظهر ويمكن مشاهدة تفاصيله**، لكن بدل قائمة الباقات يظهر له زر "🛠️ تحت الصيانة" يوضح أن الشراء غير متاح حاليًا

### إضافة منتج جديد بدون Wizard

لسه تقدر تضيف منتج بإنشاء `products/اسم-المنتج/product.json` يدويًا (كما هو موضح في القسم التالي) — كل الحقول الجديدة (`visibility`, `availability`, `badge`, `order`) اختيارية ولها قيم افتراضية منطقية، فالمنتجات القديمة (بصيغة `status: "active"`) تستمر بالعمل بدون أي تعديل.

## لوجات لوحة الإدارة

كل عملية تُنفَّذ من لوحة إدارة المنتجات تُسجَّل تلقائيًا في قناة `DASHBOARD_LOG_CHANNEL_ID`، وتشمل:

- **مين** عمل العملية (اسم العضو وصورته)
- **إيه بالتحديد** تم تغييره — مع القيمة القديمة والجديدة جنب لجنب (مثلًا `active` ➡️ `maintenance`)
- **في أي منتج** تمت العملية
- **إمتى** (تاريخ ووقت تلقائي)

العمليات المُسجَّلة: إنشاء منتج، تفعيل/صيانة، إظهار/إخفاء، تغيير Badge، تعديل الاسم/الوصف/السعر/اللون/الإصدار، تعديل الصور، تعديل المميزات، إضافة/تعديل باقة، تغيير الترتيب.

لو لم تحدد `DASHBOARD_LOG_CHANNEL_ID`، يتم تجاهل التسجيل تمامًا بدون أي تأثير على عمل اللوحة نفسها (لن يفشل أي إجراء بسبب غياب قناة اللوج).

## الأوامر

| Slash | Prefix | الوصف | الصلاحية |
|-------|--------|-------|----------|
| `/panel` | `!panel` | إرسال البانل في الروم الحالي | Owner |
| `/reload` | `!reload` | إعادة تحميل المنتجات | Owner |
| `/orders` | `!orders` | عرض آخر 10 طلبات | Owner / Dev |
| `/order id:ORD-0001` | `!order ORD-0001` | تفاصيل طلب معين | Owner / Dev |

## إضافة منتج جديد (وليس "أوردر")

ملاحظة مهمة: **"المنتج"** هو الشيء اللي تبيعه (مثلاً Interview System)، وله خطط وأسعار.
**"الأوردر"** هو طلب شراء يفتحه عميل معيّن لمنتج معيّن بخطة معينة — يُنشأ تلقائيًا، ولا يُكتب يدويًا أبدًا.

لإضافة **منتج** جديد للمتجر: أنشئ مجلد جديد داخل `products/` وملف واحد فقط بداخله: `product.json`

```json
{
  "id": "my-product",
  "status": "active",
  "name": "اسم المنتج",
  "description": "وصف قصير للمنتج",
  "color": "#5865F2",
  "features": [
```

تقدر تضيف بقدر ما تحب من الخطط داخل مصفوفة `plans` — كل خطة لازم تحتوي `name` و `price` و `currency` و `features` على الأقل. لا يوجد حد أقصى للخطط (إلا حد ديسكورد لقوائم الاختيار وهو 25 خيار).

بعد الإضافة أو التعديل اكتب `/reload` (أو `!reload`) وستظهر التغييرات فورًا في المتجر — بدون أي تعديل في الكود وبدون إعادة تشغيل البوت.

لإيقاف منتج مؤقتًا بدون حذفه، غيّر `"status"` إلى أي قيمة غير `"active"`.

### ملاحظة حول اختيار الخطط

بعد اختيار خطة، تتعطّل قائمة الاختيار بصريًا في تلك الرسالة تحديدًا (علامة أنها استُخدمت ولا يمكن تكرار الاختيار من نفسها). لو العميل أراد طلب منتج/خطة أخرى، يحتاج لفتح **تذكرة شراء جديدة** بعد إغلاق الحالية — هذا سلوك مقصود لمنع إنشاء أوردرات مكررة من نفس التذكرة.

## تحسينات V2

### أرقام التذاكر والاستلام
- كل تذكرة جديدة تأخذ رقمًا تسلسليًا مستقلًا مثل `ticket-001`.
- عند استلامها يتغير الاسم تلقائيًا إلى `ticket-001-staffname`.
- رقم التذكرة محفوظ داخليًا ولا يتغير عند إعادة تسمية القناة.
- إذا بقيت التذكرة بدون استلام لمدة `UNCLAIMED_TICKET_REMINDER_MINUTES` (افتراضيًا 10 دقائق)، يرسل البوت تذكيرًا للفريق المخصص. المؤقتات المفتوحة تُستعاد بعد إعادة تشغيل البوت.

### إدارة طرق الدفع من داخل البوت
من لوحة `/products` → **💳 طرق الدفع** تستطيع الإدارة المصرح لها:
- إضافة طريقة دفع.
- تعديل الاسم والإيموجي وتعليمات الدفع.
- تفعيل/تعطيل الطريقة.
- حذف الطريقة.

الطرق تحفظ تلقائيًا في `orders/_payment_methods.json` وتظهر للعميل فورًا بدون تعديل الكود أو إعادة تشغيل البوت.

### التقسيط
عند اختيار حالة **بانتظار الدفع** يمكن تحديد:
- السعر الأصلي.
- الخصم.
- هل الطلب بالتقسيط.
- عدد الأقساط.

يحسب النظام قيمة القسط تلقائيًا، ويسجل كل دفعة مع الموظف والتوقيت والملاحظة. ويظهر زر **تسجيل قسط** في لوج الأوردرات، وعند اكتمال قيمة الأوردر يتحول تلقائيًا إلى مدفوع.

### تاريخ العميل
يوجد زر **👤 تاريخ العميل** في لوج الأوردر. المحتوى لا يظهر إلا للإدارة المصرح لها عبر `DASHBOARD_ROLE_IDS` أو المالك، ويعرض إحصائيات وملخص آخر الطلبات.

### Transcripts
تم تبسيط رأس الـTranscript إلى بطاقات معلومات صغيرة بدل Timeline/رأس طويل، مع الإبقاء على الرسائل والمرفقات والإيمبيدات كاملة.

### Dashboard والأرقام
تم تحسين تنسيق أرقام الإحصائيات والمبيعات، وإضافة مدخل مباشر لإدارة طرق الدفع، مع الحفاظ على الـIDs الداخلية والبيانات القديمة.
